## Q&A

### Q1: Why hybrid encryption instead of pure RSA or pure AES? {#q1-why-hybrid-encryption}

RSA can only encrypt small amounts of data directly — around 245 bytes for a 2048-bit key, due to OAEP padding overhead. The payment payload here (sender VPA, receiver VPA, amount, timestamp, nonce, as JSON) doesn't reliably stay under that limit once real fields are added, and pure AES alone has no way to securely share a symmetric key with a recipient without a prior secure channel — which doesn't exist on an offline mesh network.

The fix is the same pattern used by TLS, PGP, and Signal: generate a fresh one-time AES-256 key per payment packet, encrypt the actual payload with that key using AES-GCM, then encrypt just the small AES key using RSA-OAEP with the recipient's public key. The result is one wire format: `[RSA-encrypted AES key][GCM IV][AES ciphertext + auth tag]`.

AES-GCM specifically (not plain AES-CBC) matters for the mesh context: it's authenticated encryption, meaning any tampering with the ciphertext — even a single flipped bit, whether malicious or from a bad relay hop — causes decryption to fail loudly rather than silently returning corrupted data. That's what makes it safe to let untrusted intermediate devices relay packets they can't decrypt.

### Q2: Why does the wire format need a length prefix for the RSA-encrypted key? {#q2-length-prefix}

My first draft hardcoded the RSA-encrypted key's byte length as a constant (256 bytes, correct only for a 2048-bit RSA key) inside `decrypt()`, used to know how many bytes to read off the front of the wire format before reaching the IV and ciphertext.

The problem: that hardcoded assumption breaks silently the moment the RSA key size changes (e.g. to 3072-bit, which produces a 384-byte encrypted key instead). `decrypt()` would read the wrong number of bytes and either throw a confusing exception or, worse, misparse the IV and ciphertext boundaries without any indication of what went wrong.

The fix: `encrypt()` now writes a 4-byte integer at the very start of the wire format recording the actual length of the RSA-encrypted key for that specific message. `decrypt()` reads that integer first and uses it to size its buffer correctly, regardless of what RSA key size produced it. The wire format is now self-describing instead of coupled to a hardcoded key-size assumption.

### Q3: Why generate the AES key and IV inside encrypt() instead of passing them in? {#q3-internal-key-iv-gen}

Earlier versions of `encrypt()` took `SecretKey aesKey` and `byte[] iv` as parameters, generated by whatever code called `encrypt()`. This puts a security-critical responsibility — generating a truly fresh, random key and IV for every single message — on every caller, with no guarantee they'd do it correctly. GCM in particular is unsafe if the same IV is ever reused with the same key; a caller that accidentally reused an IV (e.g. by caching it, or generating it incorrectly) would silently break the encryption's security guarantees with no visible symptom.

Moving both generations inside `encrypt()` itself — using `SecureRandom` for the IV and `KeyGenerator` for a fresh AES-256 key, every call — removes that failure mode entirely. Callers no longer need to know anything about IV/key generation correctness; they just call `encrypt()` and get a safely-generated one-time key and IV every time.

### Q4: Why hash the ciphertext for idempotency instead of comparing it directly? {#q4-idempotency-hash}

The same payment packet can arrive at the receiver more than once, since mesh gossip relays packets across multiple hops and paths — duplicate delivery is expected behavior on a lossy mesh, not an edge case. Before settling a payment, the system needs to check "have I already processed this exact packet?"

A common misconception here: hashing isn't needed because raw ciphertext comparison would be *broken* — a Base64 string of the ciphertext would actually work fine as a HashMap key on its own, since `String` already has correct `.equals()`/`.hashCode()`. The real reason to hash is practicality: SHA-256 gives a fixed-size (32-byte / 64 hex char) identifier regardless of how large the original ciphertext is, which is far cheaper to use as a HashMap key, a DB unique index, and in log output than carrying the full ciphertext around everywhere.

The hash is computed over the ciphertext specifically (not a packet ID field) because a relay node could tamper with or spoof a packet ID, but cannot forge a different valid ciphertext for the same payload without the sender's key material. So two genuinely duplicate deliveries of the same payment will always produce identical hashes, while a tampered or spoofed packet won't collide with a legitimate one.

### Q5: Why use an explicit OAEPParameterSpec instead of relying on the transformation string? {#q5-oaep-param-spec}

`Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding")` already fully specifies OAEP with SHA-256 and MGF1(SHA-256) as a transformation string, and functionally works correctly on its own. Adding an explicit `OAEPParameterSpec` on top isn't fixing a bug in this code, it's defense-in-depth: some JCE providers can parse OAEP transformation strings inconsistently, or default the MGF1 digest to SHA-1 even when the outer digest is SHA-256, unless told otherwise explicitly. Passing an `OAEPParameterSpec` object directly to `Cipher.init(...)` removes that ambiguity by pinning every OAEP parameter (digest, MGF, MGF digest, and PSource) explicitly rather than relying on string-parsing behavior that could vary across providers. It's also more self-documenting — a reader sees every OAEP parameter spelled out rather than having to know what the transformation string implies.

### Q6: Why ByteBuffer for building the wire format instead of manual byte array concatenation? {#q6-bytebuffer}

The wire format packs together four pieces of data of different, and in one case variable, lengths: a 4-byte length prefix, the RSA-encrypted AES key, the 12-byte GCM IV, and the AES ciphertext. Building this by hand would mean manually tracking offsets into a single allocated `byte[]` and copying each piece in with `System.arraycopy`, which is easy to get subtly wrong (off-by-one offsets, wrong length calculations) and hard to read back later.

`ByteBuffer` handles both directions of this cleanly. On the write side (`encrypt()`), `allocate(totalLength)` reserves exactly the right amount of space up front, and `putInt(...)`/`put(...)` write each piece in sequence while the buffer tracks the current write position internally — no manual offset math. On the read side (`decrypt()`), `wrap(wireFormat)` treats the incoming bytes as a buffer, and `getInt()`/`get(...)` read each piece back off in the same order they were written, again with the buffer tracking position automatically. This symmetry (write with `put`, read with `get`, same order) is what makes the format easy to keep correct on both ends.
